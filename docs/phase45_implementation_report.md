# Scientific Agent Phase 4.5 — implementation and verification log

Date: 2026-10-07. Baseline audit: [`phase45_capability_audit.md`](phase45_capability_audit.md). This is a live implementation log, not a claim that all Phase 4.5 batches or Phase 4 v2 are complete. V1 reports and metrics were not changed. The previously inspected Follow-up Frozen Test is historical regression data, not a new independent Test.

## Batch 1 — code-level audit (complete)

The audit found that product execution is still primarily controlled by `ScientificAgent.stream`'s Python branches. LangGraph creates a fixed plan; DeepAgents initializes a scaffold but does not dispatch the SQL/file/artifact workflow. The 9 Skill contracts are not all executable end-to-end. Evidence lacked claim-level links; Text-to-SQL had semantic binding risk; real scientific-model inference is unavailable. No new LLM call was made for the audit.

## Batch 2 — Follow-up, provenance, Evidence (implemented; targeted acceptance)

### Root causes and changes

1. `ConversationRepository.latest_analysis_context` previously selected the latest task **with Evidence**, so an immediately preceding completed/failed analysis with zero Evidence could be bypassed in favor of older data. `recent_analysis_contexts` now returns bounded recent analysis tasks regardless of Evidence, excluding only explanation-only tasks. `routes.conversation_chat_stream` resolves and persists a specific previous task ID; ambiguous multi-task references prompt for clarification with zero tool calls.
2. `ConversationContextResolver` previously used broad error matching (`异常`) and weak new-task constraints. It now uses an explicit, bounded `ConversationContextSummary`, deterministic constraints for clear cases, structured Qwen classification for ambiguity, and target-task resolution. Full unbounded history is never placed into its prompt. `evaluation/v2/followup_dev.jsonl` contains 20 new development cases; local deterministic audit was **20/20**, zero LLM calls. This is an in-development Dev score, not a frozen/generalization result. The real Qwen smoke classified “它靠谱吗？” as `EVIDENCE_EXPLANATION`; the clear trustworthiness phrasing was then constrained to `RESULT_EXPLANATION` in production. That observed mistake is not hidden by the Dev score.
3. Final answers formerly listed Evidence but did not persist a Claim→Evidence mapping. `GroundedClaim`, `ScientificAgentState.claims`, PostgreSQL `claims` table, and `evidence.local_evidence_id` now link final observation/interpretation claims to persisted Evidence UUIDs. Missing links are stored as `unsupported`; historical tasks without links are explicitly labelled as such. The UI displays these links and the persisted SQL candidate/parameters.
4. Quality gating previously returned one generic status and missed NULL, version mismatch, conflicting values, short samples, possible truncation, and failed tools. `_evidence_quality_issues` and `_finalize` now set one of `NO_DATA`, `INSUFFICIENT_EVIDENCE`, `CONFLICTING_EVIDENCE`, `EXECUTION_FAILED`, `SUPPORTED_CONCLUSION`. Empty SQL result is `NO_DATA`, never “science says absent.” A zero-count coverage claim cannot become a global undercoverage conclusion without validated scope/version. Final claims are emitted only after the gate passes.
5. `TaskRefinementPatch` extracts explicitly changed dataset/model version, subgroup, and output format. Data-changing refinements enter a new Agent task with a `previous_task_id` link; only formatting-only table requests reuse persisted SQL rows without another tool call. Version-changing requests do not inherit old Evidence.
6. A real four-turn smoke initially failed on a Qwen SQLCandidate whose SQL used `%(dataset_version)s` but whose `params.dataset_version` was the literal string `%(dataset_version)s`. The guarded read-only query returned 0 rows. `TextToSQLService.generate` now binds the trusted HITL/request dataset version when that placeholder is present; a missing placeholder is rejected before execution. This is the minimum upstream correction required to complete Batch 2's real smoke, not a claim that all Text-to-SQL semantic defects are fixed.

## Batch 3 — Planning, Replanning, Recovery, durable HITL (targeted acceptance)

`planning_graph.create_plan` now emits typed, dependency-bearing steps for complex database tasks (Schema → SQL generation/check → read-only execution) and the mixed file→subgroup→database workflow. `ScientificAgent._start_plan_step` enforces prerequisites before actual tool branches run; observations and Evidence IDs are attached to executed steps. This is a genuine execution gate for these flows, though DeepAgents is still an auxiliary scaffold, not the SQL/file dispatcher.

`recovery.classify_failure` separates invalid arguments, schema mismatch, timeout, rate limit, permission, unavailable tool, empty result and non-retryable errors. `bounded_transient_retry` applies exponential backoff only to retryable failures of idempotent operations; the outer task timeout and max-tool budget remain active. A PostgreSQL `EXPLAIN` missing-column observation triggers at most one SQL repair with bounded feedback, duplicate-candidate guard and explicit `PLAN_REVISED` (`original_plan`, observation, reason, revised plan). A repaired failure is marked recovered so it does not invalidate good Evidence; an unrecovered one fails safely. Empty results never trigger an unscoped broader query.

HITL Resume is atomically claimed in PostgreSQL only from `waiting_for_user`, with a seven-day freshness limit. Duplicate/concurrent/wrong-thread/expired Resume is rejected; waiting or running tasks may be cancelled; the unscoped legacy Resume route cannot bypass a persisted task. Cancellation and terminal answer persistence race through database status compare-and-swap, so a late answer cannot overwrite a cancellation. An in-flight tool is not forcibly killed; the stream cooperatively stops when it yields its next event. A configured but unavailable Postgres checkpoint store now refuses volatile in-memory HITL rather than silently downgrading durability. Tests cover backend recreation, concurrent claim, repeat/expired/cancelled Resume, re-interruption, failure after Resume, and cancellation versus final answer. The UI exposes pending/running cancellation and historical `PLAN_REVISED`/Claim→Evidence/Follow-up traces.

## Batch 4 — executable Scientific Skill (targeted acceptance, catalog expansion deliberately limited)

The original nine Skill files remain intact. The audit found that their documentation was richer than the actual Python dispatch. One new Skill, `cross_dataset_comparison`, was added only because the existing `training_molecules` and `molecules` tables can support a real read-only comparison. Its selection requires an explicit comparison and two distinct training versions. In the product stream, the Skill runs capability/permission checks, validates the required schema, SQLGlot + database `EXPLAIN`, executes a parameterized read-only grouped query, preserves raw rows, calculates per-structure counts/denominators/shares/deltas and emits two Evidence records. A missing version or unsupported quality/performance question is insufficient evidence, not a fabricated result. The Skill composes with the existing `training_coverage_analysis` selection.

Seven new `test_cross_dataset_skill.py` cases cover normal operation, routing negative examples, incomplete versions, authorization/tool failure, missing schema, unsupported dimensions and composition. The real PostgreSQL smoke returned 6 rows, 2 Evidence, `SUPPORTED_CONCLUSION`; tool selection used the configured `qwen3.7-flash` structured output and did not fall back. The selector now captures the actual completion's model/usage plus invocation latency. One no-thinking smoke observed **169 input / 151 output / 320 total tokens, 2723.03 ms** for the tool-selection call only. An earlier one-call smoke before no-thinking observed **167 / 400 / 567 tokens, 6500.66 ms**; these are individual observations, not a controlled performance estimate. HTTP status is not exposed by this SDK wrapper and remains unmeasured. No rerun of old Skill Frozen Test has been presented as a new score. The catalog is 10, not a forced 14–15: distribution shift, annotations and spectrum quality remain partial/blocked without rigorous data and tools.

## Batch 5 — Tool arguments, SQL binding, Artifact and mixed-resource correctness (targeted acceptance)

The previous `ToolSpec` helper typed every required argument as string and allowed arbitrary additional properties, including for `filenames`, `metrics` and result `rows`. This directly contradicted the actual Python call contracts and allowed invalid selections. Those schemas now use arrays/objects/enums/bounds where appropriate, disallow undeclared fields, and are validated with JSON Schema before accepting a selected ToolCall. An invalid LLM choice is not treated as executable. `SQLGuard.validate_bindings` requires an exact set of non-null named parameters before query checking or execution. Existing SQLGlot read-only/table guard, PostgreSQL `EXPLAIN`, read-only role and conditional one-time repair remain in place; this is not a claim of general SQL semantic correctness.

Artifact table creation now refuses empty rows, missing required columns and inconsistent row schemas. A content-level test reads generated CSV/XLSX back and checks exact values plus per-task object-key isolation; PNG signature remains covered. Mixed file+database tasks with an explicit `train_vN` additionally perform a bounded parameterized `molecule_id` join against that version, preserving file-side keys, raw DB join Evidence and a reconciliation summary when rows exist. A successful controlled join test verifies the final Claim cites all three Evidence IDs. The actual demo model CSV uses `M...` IDs while the training fixture uses `T...` IDs; the PostgreSQL integration test observes an empty join and correctly reports insufficient evidence. These fixtures must not be presented as a successfully linked scientific cohort.

The first real Qwen mixed-resource smoke exposed two additional failures. Qwen's `RequestIntent` incorrectly narrowed an explicit CSV+`training_db` request to `database_analysis`, causing unnecessary dataset-version HITL even though `train_v3` was in the query. `RequestRouter.route_async` now preserves the deterministic mixed-resource constraint for explicit file+database requests, and `ScientificAgent.stream` binds a uniquely named version before considering HITL. A later smoke reached SQL but returned 0 rows because the full mixed file+model goal was supplied to database Text-to-SQL; another attempt hallucinated a `dual` table and propagated a checker exception. The database step now receives a focused training-coverage subgoal. A generated disallowed table is treated as a *bounded schema-repair candidate* by SQLGlot Guard, never executed, and exhausted/duplicate repair paths produce a persisted safe final answer instead of an uncaught exception. Tests cover both routing/version constraints and the hallucinated-table repair path.

An initial successful real `qwen3.7-flash` mixed smoke (no full benchmark) reached `mixed_analysis` with no HITL, generated a parameterized `train_v3` SQLCandidate via `llm_structured_output`, executed PostgreSQL SQL successfully with **4 rows**, then executed the versioned file–DB join read-only with **0 rows** (the known ID mismatch). Final status was `INSUFFICIENT_EVIDENCE`, 7 Evidence records were present (file/MCP/DB/query-side evidence), and tool selection telemetry observed 177 input / 117 output / 294 total tokens, 2106.67 ms, fallback=false for **that one call**. That first smoke did not capture SQL usage or whole-stream latency. The earlier real smoke failures remain part of the record.

Subsequent telemetry identified a 28.24 s, 4,625-token thinking-mode SQL generation on one smoke. The mixed DB plan now supplies only the two required tables/relationship and a focused SQL subgoal; Qwen structured SQL generation uses no-thinking while retaining SQLGlot/EXPLAIN and one conditional repair. A later same-query smoke still returned 4 valid SQL rows and the expected 0-row join, with **635 SQL tokens / 2054.24 ms**, **271 tool-selection tokens / 1678.13 ms**, **906 measured total LLM tokens across those two calls**, **10,671.05 ms Agent stream latency**, **2.21 ms time-to-first-progress**, and fallback=false for both observed calls. The earlier thinking-mode smoke had 4,625 SQL plus 263 selector tokens. These are different single-run observations with server variance; they do **not** establish a statistically valid token/latency improvement or P95. HTTP status and current price remain unmeasured.

The final backend regression after route/SQL refinements was **112 passed in 80.05 s**; the subsequently added static v2 scenario-validator test passed separately. A prior suite run had one obsolete test expectation that explicit mixed-resource routing would be labelled an LLM fallback; the new constrained route deliberately skips that LLM call, the expectation was corrected, and the clean run followed. Vue's 4 history-loading tests and production build passed. No v2 aggregate metric or cost improvement is claimed from these targeted checks.

### Remaining risk before broader claims

Follow-up rules were tuned on 20 Dev examples; a new scenario/template-disjoint Frozen Test remains to be created in Batch 6. Claim links cover new final answers, not a retroactive reconstruction of historic answers. The quality gate does not yet prove SQL semantic correctness or population-level causal inference. No TC-TopoRT or chenmt-ms checkpoint/preprocessing package was found in this project; `predict_rt` remains unavailable even if `MODEL_PATH` is set. The only other discovered `.safetensors` file in `D:\工作` belongs to a text embedding model in a separate Aix-DB repository and is not a scientific predictor. Do not advertise scientific model inference as implemented. General Skill execution, semantic SQL validation, production cohort alignment, latency telemetry and full Phase 4 v2 evaluation remain open.

## Batch 6 — v2 preparation, not a completed evaluation

The new protocol and status report are in `docs/phase4_v2_evaluation_protocol.md` and `docs/phase4_v2_evaluation_report.md`. `evaluation/v2/scenario_cases.jsonl` has 15 Dev and 15 `test_draft` cases across the required scenario families; a static validator confirms unique IDs, family coverage, template-label non-overlap and no exact normalized prompt reuse. Full v2 evaluation metrics are therefore **not available**. No old V1 metrics or labels were overwritten.
